## medium: Bot token accepted via command-line argument is exposed in process list and shell history

id: fnd_sig-feat-library-25faef2bc4-1c92_70271b1f5e
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python source root (feat_library_25faef2bc4)

evidence:
- update_bot_button.py:34-35 (main)
- update_bot_button.py:53-56

The failure message instructs the user to pass the bot token as a positional CLI argument, and the __main__ block writes sys.argv[1] into TELEGRAM_BOT_TOKEN. Credentials passed via argv are visible in ps/top output for the process lifetime, persist in shell history, and are echoed into CI logs and shell wrappers. The script already supports TELEGRAM_BOT_TOKEN/BOT_TOKEN env vars plus .env and config.json fallbacks, so the argv path is an unnecessary credential-exposure vector. The argv value also mutates the process environment, so any child process inherits the secret.

recommendation:
Remove the argv token path (lines 53-56) and the usage hint (line 35). Require the token via TELEGRAM_BOT_TOKEN/BOT_TOKEN env vars or the existing .env/config.json fallbacks, or read it from stdin without echoing (e.g., getpass).

test analysis:
The feature ships with no tests (tests: []), and the argv override is only exercised in ad-hoc manual runs.

suggested regression test:
A unit test that monkeypatches os.environ and asserts get_token() prefers TELEGRAM_BOT_TOKEN over .env/config.json and that no token is accepted from sys.argv, so the argv path can be removed without regressing env-based resolution.

minimum fix scope:
update_bot_button.py lines 34-35 and 53-56

repro:
Run `python3 update_bot_button.py 1234567890:ABCD...` and observe the full token in `ps aux` output and in shell history; any CI step that echoes the command will also log the token.

## low: Unhandled exceptions in token loading and Bot construction bypass the friendly error path

id: fnd_sig-feat-library-25faef2bc4-99cb_41f9950f67
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Python source root (feat_library_25faef2bc4)

evidence:
- update_bot_button.py:16-25 (get_token)
- update_bot_button.py:38 (main)

open()/read() on .env and config.json (lines 16-25) can raise PermissionError/OSError if the files exist but are unreadable, and Bot(token=...) at line 38 raises ValueError/TypeError for a malformed, empty-after-strip, or stale token. All of these run outside the try/except at lines 39-50, so the script aborts with a raw traceback instead of the intended user-facing message, and a constructor failure skips the session-cleanup path entirely. These failure modes are realistic because tokens are read from mutable local files and can be edited or stale.

recommendation:
Wrap token loading and `bot = Bot(token=token)` inside the existing try/except (or validate the token format before construction) and print the friendly error message on failure; keep session close in a finally that only references bot when construction succeeded.

test analysis:
No tests exist for the script, so the malformed-token and unreadable-file paths are never exercised.

suggested regression test:
A pytest test that monkeypatches Bot to raise ValueError on construction and asserts main() prints the friendly error instead of propagating a traceback.

minimum fix scope:
update_bot_button.py lines 16-25 and 38

repro:
Set TELEGRAM_BOT_TOKEN to a malformed value such as `not-a-token` and run the script: Bot() raises outside the try block and the process exits with a traceback.

## low: Hardcoded absolute token-source paths tie the script to this machine

id: fnd_sig-feat-library-25faef2bc4-3e11_0bebeedce7
category: maintainability
confidence: medium
triage: risk
status: open
feature: Python source root (feat_library_25faef2bc4)

evidence:
- update_bot_button.py:15 (get_token)
- update_bot_button.py:22 (get_token)

The .env and config.json lookups hardcode /root/openclaw/ and /root/.openclaw/ paths. If the workspace moves, is cloned elsewhere, or the script runs in a container or CI, get_token() silently degrades to env-only resolution or returns None, making token discovery fail without an obvious cause.

recommendation:
Resolve the .env and config paths relative to the script (e.g., Path(__file__).resolve().parent) or accept them via parameters/env, keeping the current absolute paths as fallbacks for compatibility.

test analysis:
No tests exercise token resolution outside this machine's fixed paths; behavior is only validated manually on this host.

suggested regression test:
Refactor get_token(paths=None) to accept paths as parameters and add tests using tmp_path to verify resolution without /root/openclaw.

minimum fix scope:
update_bot_button.py lines 15 and 22
